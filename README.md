**Диагностика производительности Minecraft-сервера человеческим языком. Сделано для владельцев серверов.**

Spark отлично профилирует, но выдаёт дерево вызовов методов, в котором владелец сервера ничего не понимает. LagLens показывает то же самое простыми словами: **где именно лагает и что с этим делать**.

> **English:** a Paper 1.21 plugin that explains server lag in plain language. `/lagreport` finds overloaded chunks (tile entities, hoppers), worlds with too many entities or dropped items, and reports TPS/MSPT with a concrete fix for each problem. The chunk scan is spread across ticks, so the diagnostic tool never causes the lag spike it is looking for.

---

## Пример отчёта

Вывод команды `/lagreport`:

```
LagLens
TPS 14.2 (1м) / 16.8 (5м) / 18.1 (15м)   MSPT 68.4

Найдено 2 проблемы:

[1] Чанк (312, -88) в world - 267 тайл-энтити (41% всех на сервере)
    из них 267 хопперов
    → Сократить число хопперов или заменить связки на воронки-фильтры; разнести сортировщики по разным чанкам.

[2] Мир world_nether - 1840 сущностей
    из них 1204 брошенных предметов
    → Настроить despawn предметов (item-despawn-rate), проверить незакрытые ловушки мобов.

Загружено чанков: world 1284 | world_nether 312 | world_the_end 48
```

## Установка

1. Скачайте `LagLens-<версия>.jar` из раздела [Releases](../../releases).
2. Положите файл в папку `plugins/` вашего сервера.
3. Перезапустите сервер. При первом запуске рядом появится `plugins/LagLens/config.yml`.

**Команды:**

- `/lagreport` - снимок состояния сервера с отчётом о проблемах. Итог сохраняется в историю.
- `/lagreport history [число]` - последние сохранённые отчёты и чанки, которые повторяются от отчёта к отчёту.

```
LagLens - история отчётов
02.10 21:40  TPS 14.2  MSPT 68.4  проблем: 2  худший чанк (312, -88) world
02.10 19:05  TPS 19.8  MSPT 22.1  проблем: 1  худший чанк (312, -88) world
01.10 23:12  TPS 20.0  MSPT 18.7  проблем: 0

Повторяются от отчёта к отчёту:
  чанк (312, -88) в world - в 2 сохранённых отчётах
```

**Право:** `laglens.use` (по умолчанию выдано операторам).

## Конфигурация

Файл `plugins/LagLens/config.yml`. Все пороги - это границы, при которых показатель считается проблемой и попадает в отчёт.

```yaml
scan:
  # Сколько чанков обрабатывать за один тик. Меньше - безопаснее для TPS, но скан дольше.
  chunks-per-tick: 200

thresholds:
  # Чанк попадает в отчёт, если тайл-энтити в нём не меньше этого числа.
  chunk-tile-entities: 50
  # Отдельный порог для хопперов в одном чанке - частая причина лагов.
  chunk-hoppers: 100
  # Мир помечается проблемным, если сущностей в нём не меньше этого числа.
  world-entities: 1000
  # Порог брошенных предметов в мире - признак незакрытой ловушки.
  world-dropped-items: 500
  # TPS ниже этого значения считается просадкой (норма - около 20).
  tps-warning: 18.0
  # MSPT выше этого значения = тик не укладывается в бюджет 50 мс.
  mspt-warning: 45.0

report:
  # Сколько «горячих» чанков показывать.
  top-chunks: 5
  # Сколько перегруженных сущностями миров показывать.
  top-entity-clusters: 3

history:
  # false - отчёты строятся, но не сохраняются.
  enabled: true
  # Сколько последних отчётов хранить; более старые удаляются при записи.
  keep: 200
  # Сколько отчётов показывать по /lagreport history без числа.
  shown: 5
```

## Как это устроено

Это ключевой раздел: он объясняет, почему написать такой плагин наивно - значит **самому создать лаги**, которые ты пытаешься диагностировать.

### Проблема

Чтобы найти перегруженный чанк, нужно обойти все загруженные чанки и в каждом вызвать `getTileEntities()`. На большом сервере это тысячи чанков. Если сделать это **в одном тике**, обход займёт десятки миллисекунд - при бюджете тика в 50 мс это гарантированная просадка TPS. Получается диагностический инструмент, который сам вызывает тот самый лаг-спайк, что ищет.

Плюс к этому Bukkit API **не потокобезопасен**: чанки, миры и сущности можно читать только из главного потока. «Просто увести скан в отдельный поток» - нельзя.

### Решение

Скан размазан по тикам через планировщик сервера:

- В начале берётся **снимок** списка загруженных чанков.
- Каждый тик обрабатывается порция в `chunks-per-tick` чанков (по умолчанию 200, значение настраивается). Нагрузка на один тик остаётся маленькой.
- Промежуточный результат копится между тиками; отчёт отдаётся только по завершении полного обхода.
- Пока скан идёт, повторный вызов `/lagreport` **не запускает второй скан** - иначе два обхода сложились бы в один спайк.
- Если чанк выгрузился за время скана - он пропускается, к нему не обращаются (чтобы не загрузить его обратно и не создать новую нагрузку).
- Если игрок, вызвавший команду, вышел - отчёт не отправляется в никуда.

Тяжёлым остаётся только обход чанков. TPS, MSPT и подсчёт сущностей - дешёвые операции, они собираются синхронно за один тик.

### Про MSPT

MSPT берётся из `Server#getAverageTickTime()`, TPS - из `Server#getTPS()`. Оба метода есть в Spigot-API, поэтому доступны и на Paper без рефлексии. На экзотическом сервере без этих методов вызов перехватывается и MSPT показывается как «н/д» - команда не падает.

### История отчётов

Один отчёт показывает, что не так сейчас. Чтобы отличить разовый всплеск от постоянной проблемы, итог каждого отчёта сохраняется в `plugins/LagLens/history.db` - файл SQLite. Отдельный сервер базы не нужен, драйвер SQLite входит в состав Paper.

- **Две таблицы.** `reports` - по строке на отчёт (время, TPS, MSPT, число проблем, чанки и сущности). `hot_chunks` - «горячие» чанки отчёта со ссылкой на него; при удалении отчёта его чанки удаляются каскадом.
- **Запись в одной транзакции.** Отчёт, его чанки и удаление записей сверх `history.keep` либо применяются вместе, либо не применяются вовсе.
- **База не трогает главный поток.** Диск может ответить за миллисекунду, а может за секунду. Запросы уходят в отдельный поток `LagLens-History`, результат чтения возвращается в главный через планировщик. При выключении плагин дожидается записей из очереди.
- **Повторяющиеся чанки** считает запрос с `GROUP BY` по миру и координатам: в список попадают чанки, которые встретились больше чем в одном отчёте.
- **Отказ базы не ломает плагин.** Если файл не открылся, отчёты строятся как раньше, а в консоль уходит предупреждение.

Хранилище (`storage/ReportHistory`) не зависит от Bukkit и покрыто тестами: чтение записанного, порядок и лимит, каскадное удаление, подсчёт повторов, повторное открытие файла. Тесты идут при каждой сборке: `./gradlew test`.

### Важная честность про «% нагрузки чанка»

LagLens **не** показывает «сколько процентов времени тика съел чанк» - для этого нужен профайлер (это делает Spark). Вместо выдуманного тайминга показывается **измеримый структурный факт**: доля тайл-энтити чанка от всех на сервере. Это эвристика («вот аномальное скопление»), а не замер времени, и в отчёте она названа честно.

## Что это НЕ делает

- **Не заменяет Spark.** Не профилирует методы и не строит стектрейсы. LagLens отвечает на вопрос «что в мире не так», а не «какой метод тормозит».
- **Ничего не удаляет и не меняет.** Плагин только читает состояние сервера. Никакой автоочистки сущностей, кила предметов или изменения настроек - решения принимает владелец.
- Нет веб-панели и графиков. История - это список последних отчётов, а не мониторинг: запись появляется только после команды `/lagreport`.
- Нет поддержки Bungee/Velocity, PlaceholderAPI, bStats.

## Совместимость

- **Сервер:** Paper 1.21.x (работает и на совместимых форках Paper).
- **API:** Paper API (`api-version: 1.21`).
- **Java:** 21.
- **Сборка:** Gradle (Kotlin DSL).
